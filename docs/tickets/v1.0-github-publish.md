## Why hold

The standing rule is: never push to GitHub without per-action authorization. The v1.0 commits include the actual binary signature + Info.plist keys that Apple is currently reviewing. If Apple rejects the submission and asks for a re-submit with changes, the corresponding GitHub commit list might shift.

Tagging `v1.0.0` BEFORE approval risks the situation where:
- You tag v1.0.0
- Apple rejects, asks for a fix
- You commit the fix as `v1.0.1` even though it's the actual "v1.0" Apple eventually approved
- Future user "what's v1.0" confusion

Waiting until approval keeps the GitHub tag aligned with what Apple actually shipped.

## v1.0.x backlog — known limitations to address after first ship

Below are real product issues discovered during the 2026-05-28 ship-day sanity checks. None block v1.0 review. All worth fixing in a v1.0.1 or v1.1 release once the App Store version is live and we know there are no review-cycle regressions to focus on first.

### 1. ✅ DONE — Discovery filters link-local + self-Tailscale results

**Status:** Implemented + tested in commit (after v1.0.0 tag) on `main`. Pending v1.0.1 release.

**Symptom (resolved):** Clicking Settings → Discover surfaced ghost entries like:

- `http://169.254.226.184:11434 (Ollama)` — IPv4 link-local auto-config
- `http://[fd7a:115c:a1e0::7d3b:2a72]:11434 (Ollama)` — Tailscale IPv6 ULA reflecting back

These are network interfaces on the *probing* machine itself responding via mDNS/Bonjour. They look like "new servers" to the user but they're actually the user's own Mac responding to its own probe. Adding them to the config makes the menu look broken (Unreachable for no apparent reason).

**Cause:** `Discovery.scan()` in `ModelStatus/Discovery.swift` probes the `/24` LAN and Tailscale peers without filtering out:

- `169.254.0.0/16` (IPv4 link-local — RFC 3927, auto-config only)
- `fe80::/10` (IPv6 link-local)
- The probing machine's own Tailscale IP (in the `100.64.0.0/10` CGNAT range OR the `fd7a:115c:a1e0::/48` ULA)

**Fix sketch:**

```swift
// In Discovery.swift, after collecting the result list:
private static func isSelfTailscaleIP(_ host: String) -> Bool {
    // Compare against `tailscale ip` for this machine OR check against
    // the local interface's IPv6 ULA prefix.
    ...
}

let filtered = results.filter { r in
    let host = URL(string: r.url)?.host ?? ""
    if host.hasPrefix("169.254.") { return false }       // IPv4 link-local
    if host.hasPrefix("fe80:") { return false }          // IPv6 link-local
    if isSelfTailscaleIP(host) { return false }          // self-tailnet IP
    return true
}
```

**Acceptance criteria:**

- [x] Discover from a machine with active Tailscale + link-local IPv4 → result list excludes both
- [x] Manual entry via Settings → Add still allows link-local URLs if a user explicitly wants one (filter only applies to Discovery results, not manual Add)
- [x] 8 unit tests (`Tests/ModelStatusTests/DiscoveryTests.swift`) covering link-local IPv4, link-local IPv6, near-misses, ULA non-filtering, self-IP match, loopback aliases, bracket stripping, and the real-world regression case
- [x] 76 tests total passing (was 68 at v1.0.0 ship)

### 2. OpenAI-compatible provider can't detect Active vs Idle accurately

**Symptom:** When the MLX server is actively serving (e.g., police-db's dept-extract hitting `Qwen3.5-9B-MLX-4bit` for 25+ min straight), ModelStatus reports it as `Active` because the registry has 3 models, but cannot distinguish "actively generating" from "registered but resting."

**Cause:** `OpenAIProvider.check()` only probes `/v1/models` (which returns the registry of available models). The OpenAI HTTP API has no standardized "what's loaded in RAM right now" or "queue depth" endpoint.

**Fix sketch (pick one or both):**

- **Approach A — vLLM-only:** vLLM exposes `/metrics` in Prometheus format with `vllm:num_requests_running`, `vllm:gpu_cache_usage_perc`, etc. The existing `vllm` provider variant could be enhanced to parse these and surface them as live stats.
- **Approach B — generic activity probe:** Track request-rate by polling the provider's listening socket from outside. If response latency to `/v1/models` jumps from 10ms → 200ms while the model list itself is unchanged, that's a signal that the server is under load. (Less precise but works for all OpenAI-compat servers including MLX, Llamafile, LM Studio.)
- **Approach C — MLX-specific:** Check if `mlx_lm.server` exposes any custom endpoints we could ping. Investigate the mlx-lm repo for any non-standard introspection routes.

**Acceptance criteria:**

- [ ] User can look at the menu and tell whether the MLX server is generating tokens RIGHT NOW or just sitting idle
- [ ] Doesn't introduce false-positive "Active" reports from misinterpreting normal traffic patterns

### 3. Settings table doesn't auto-prune obviously stale entries

**Symptom:** If a user accidentally adds a ghost entry (via Discovery clicking through, or by manually entering an unreachable URL), it stays in the config forever showing as Unreachable, cluttering the menu.

**Possible fix:** Add an opt-in "Auto-remove servers Unreachable for >7 days" toggle in Settings. Disabled by default so we don't surprise users by deleting legitimate servers that happened to be down.

### 4. URLSession rotation interval (5 min) might be too aggressive for slow networks

**Symptom:** None observed yet, but on slow networks (especially `.local` mDNS resolution which can take a few seconds the first time), rotating the session every 5 minutes might cause a brief Unreachable blip every 5 minutes.

**Possible fix:** Track failure streaks per-instance. Rotate the session only when at least one instance has had >3 consecutive failures, rather than on a pure timer.

### 5. Provisioning profile (for TestFlight)

### 6. Generic HTTP "health" provider (monitor non-model servers)

**Status:** DESIGN — plan only, build later (planned 2026-06-01).

**Motivation:** Real case on the M4 Pro — a NuExtract extraction server (`uvicorn nuextract_server:app --port 8090`) was actively using the GPU, but ModelStatus showed nothing. It's a plain FastAPI app: `/v1/models` → 404, `/api/tags` → 404, only `/health` (200) and `/docs`. None of the existing providers (ollama / openAI / lmStudio / vllm / mlx) recognize it because they all key off model-list endpoints. Users running bespoke inference/extraction services, embedding servers, RAG backends, or any HTTP service want a "is it up, and is it busy?" indicator without that service having to speak the OpenAI API.

**Goal:** A new `ProviderKind.httpHealth` (display "HTTP service") that monitors *any* HTTP endpoint by reachability + latency, with no model-list assumptions.

**Design:**

- **New provider `HTTPHealthProvider: Provider`**
  - `capabilities = []` (no eject/load/listAvailable/VRAM). It is purely a reachability+activity probe.
  - `probe`: GET the configured health path (default `/health`, user-overridable), success = any 2xx **or** 3xx (many health endpoints 200; some bare apps only answer 200 on `/`). Configurable expected-status is a later nicety; start with "2xx/3xx = up".
  - `check`: GET health path, map to state:
    - non-2xx/3xx or no response → `.unreachable`
    - reachable → `.idle` by default; `.active` when the **latency-delta heuristic** trips (see below). Never `.generating` — that's model-specific and we don't lie (same rule as the OpenAI provider).
  - No `/v1/models` or `/api/ps` calls — those 404s are exactly why this kind exists.

- **Activity heuristic (borrowed from backlog item #2, Approach B):** track a rolling baseline of health-probe latency per instance. If current latency jumps materially above baseline (e.g. > 3× rolling median AND > some floor like 150ms), report `.active` ("busy"); otherwise `.idle` ("up"). This is best-effort — document it as a heuristic, never a hard claim. A server with a trivially-fast `/health` that does real work elsewhere may always read idle; acceptable. Keep the baseline state in `Monitor.InstanceState` (new fields: `healthLatencySamples` ring buffer or just `medianLatencyMs`).

- **Config / Instance:**
  - Reuse the existing `Instance` — `kind = .httpHealth`. Add an optional `healthPath: String?` (default `/health`) so the user can point at `/`, `/healthz`, `/status`, etc. Backward-compatible Codable like the v1.0.1 lifecycle fields.
  - Auto-detect (`.auto`) should **not** silently classify everything as httpHealth — keep it as an explicit user choice in the Add/Edit dropdown, because a catch-all health provider would shadow real model-server detection. `.auto` probe order stays model-servers-first; httpHealth is opt-in only.

- **Discovery:** do **NOT** add httpHealth to the `Discovery.probeMatrix`. A health-only probe accepts almost any HTTP 200 and would flood discovery with false "servers" (web UIs, dashboards, routers). Generic-health instances are added manually with an explicit port + path. (Revisit later if there's demand for a separate "scan for HTTP services" mode — out of scope.)

- **Menu rendering:**
  - Header: ● green "Up" / dimmed "Idle" / heuristic "Busy", ✗ red "Unreachable" — reuse `statusInfo` with httpHealth-aware labels (no model/VRAM rows since caps are empty).
  - Show latency (already in `ServerStatus.latencyMs`) as the one useful detail line: "⚡ 240ms" when busy.
  - Plays nice with the v1.0.1 dormant lifecycle automatically — an httpHealth instance that goes down ages to dormant → archived like any other.

- **CLI:** `ModelStatus status [--json]` already renders any `ServerStatus`; an httpHealth instance shows `detectedKind: "httpHealth"`, `state: up/idle/busy/unreachable`, empty `loadedModels`. No CLI change needed — free.

- **Security:** same URL validation + SSRF guards as existing providers (it goes through `HTTPHelpers.get`, `DNSResolutionGuard`). The configurable `healthPath` must be path-only — validate it starts with `/` and reject schemes/hosts in it (no `healthPath = "http://evil/"`).

- **Sandbox/App Store:** pure HTTP — identical behavior sandboxed. No new entitlements.

**Acceptance criteria:**
- [ ] User can add a server with kind "HTTP service" + custom health path and see Up/Unreachable in the menu
- [ ] A busy backend (sustained latency spike) reads "Busy"; an idle-but-up one reads "Idle"
- [ ] No false positives in Discovery (httpHealth never auto-discovered)
- [ ] `/v1/models`-less servers (like NuExtract on :8090) work when added manually
- [ ] Heuristic documented as best-effort; never reports "Generating"

**Note on the motivating case:** NuExtract on the M4 Pro binds `127.0.0.1` — to monitor it from another machine it must bind `0.0.0.0`/Tailscale first. That's a change to *that server's* launch args, independent of this feature.
